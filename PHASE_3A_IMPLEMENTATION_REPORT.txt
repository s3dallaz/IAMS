================================================================================
ARCHITECTURE & DESIGN
================================================================================

1. LivenessState Enum
   ------------------
   - LIVE: Face determined to be a live person
   - SPOOF: Face determined to be a spoofing attempt
   - UNKNOWN: Insufficient evidence to determine liveness
   
   Design Decision: Using enum ensures type safety and clear state representation.

2. LivenessResult Data Class
   --------------------------
   Attributes:
   - state: LivenessState (LIVE, SPOOF, or UNKNOWN)
   - confidence: float (0.0 to 1.0)
   - frame_count: int (number of frames analyzed)
   - reason: str (human-readable explanation)
   
   Validation:
   - Confidence must be between 0.0 and 1.0
   - Frame count cannot be negative
   
   Design Decision: Similar to RecognitionResult pattern, provides complete
   context for liveness determination.

3. LivenessDetector Class
   -----------------------
   Initialization Parameters:
   - min_frames: Minimum frames required for reliable detection (default: 10)
   - liveness_threshold: Confidence threshold for LIVE determination (default: 0.75)
   - temporal_window_seconds: Time window for temporal analysis (default: 2.0)
   
   Public API:
   - detect_liveness(frame, detected_face) -> LivenessResult
     Single-frame liveness detection (foundation only)
   
   - detect_liveness_sequence(frames, detected_faces) -> LivenessResult
     Multi-frame temporal liveness detection (foundation only)
   
   Design Decision: API supports temporal analysis across multiple frames,
   which is more robust than single-frame detection. This anticipates the
   requirements of Phase 3B/3C algorithm implementation.

4. Input Validation
   ----------------
   Frame Validation:
   - Must be numpy array
   - Cannot be None or empty
   - Must be 2D (grayscale) or 3D (color)
   - Minimum dimensions: 10x10 pixels
   
   DetectedFace Validation:
   - Must be DetectedFace instance
   - Must have valid bbox (4 values: x, y, width, height)
   - Bbox dimensions must be positive
   - Confidence must be between 0.0 and 1.0
   
   Sequence Validation:
   - Both frames and faces must be provided
   - Must be lists
   - Must have matching lengths
   - Cannot be empty
   - Each element must pass individual validation
   
   Design Decision: Comprehensive validation prevents downstream errors and
   ensures clean error messages for debugging.

5. Error Handling & Safe Failure
   ------------------------------
   LivenessDetectionError Exception:
   - Raised for validation failures
   - Raised for invalid input types
   - Provides clear error messages
   
   Safe Failure Behavior (Phase 3A):
   - Always returns UNKNOWN state (not LIVE)
   - Confidence = 0.0
   - Clear reason indicating Phase 3A foundation only
   
   Critical Safety Property:
   Phase 3A NEVER returns LIVE state without evidence. This is verified
   by tests test_detect_liveness_phase_3a_safe_failure and 
   test_detect_liveness_sequence_phase_3a_safe_failure.
   
   Design Decision: Failing safe is critical for security. An attendance
   system must not accidentally mark spoofed faces as live.

================================================================================
INTEGRATION WITH EXISTING SYSTEM
================================================================================

The LivenessDetector integrates seamlessly with the existing CV pipeline:

Current Pipeline:
    CameraManager
        ↓
    FaceDetector (returns DetectedFace)
        ↓
    FaceEmbedder
        ↓
    FaceRecognizer

Phase 3A Foundation:
    FaceDetector (returns DetectedFace)
        ↓
    LivenessDetector (accepts frame + DetectedFace)
        ↓
    Returns LivenessResult

Future Integration (Phase 3B+):
    CameraManager
        ↓
    FaceDetector
        ↓
    LivenessDetector (temporal analysis across frames)
        ↓
    If LIVE → FaceEmbedder → FaceRecognizer → Attendance
    If SPOOF → Reject / Log unknown face
    If UNKNOWN → Request more frames or reject

The API is designed to support this future integration without breaking changes.
